Cached row policy

Orders are scoped by a policy whose decision is too slow to run per row in SQL: it asks another system which regions this caller may see. So it runs on the server, once per row, and the server remembers the answers; the query carries only a membership test over the rows this caller may see. The counter is what that saves: it goes up when a decision is made.

Grants

Revoking a region changes nothing about any order, so no version column could notice. The server tells the cache, and the next query decides every row again.

    What to try

    • Run the query again. The rows come back and the counter stays: every row was decided already.
    • Revise an order. Its revision moves past the one this caller was decided up to, so the next query decides that row alone: the counter goes up by one.
    • Revoke a region. Its rows go, and the counter goes up by every row: the caller's answers were made again.
